# Учебный проект на Go

В проекте три Go-модуля: корневой пример, Gateway и Ledger.
Gateway импортирует Ledger через `require` и локальный `replace` в `gateway/go.mod`.

## Тема 6. Тестирование

Тесты используют стандартную библиотеку Go, без внешних зависимостей.

- `ledger/validation_test.go`: table-driven unit-тесты `Transaction.Validate`,
  `Budget.Validate` и `CheckValid`. Независимые тесты и их подзадачи `t.Run`
  вызывают `t.Parallel()`, поскольку не используют общее хранилище.
- `ledger/ledger_test.go`: бюджет 5000, добавление в пределах лимита и ровно
  до лимита, превышение общей суммы, отказ без изменения списка, обновление
  бюджета, загрузка JSON, ошибки чтения, копии коллекций и сброс ID.
- `gateway/internal/api/handlers_test.go`: интеграционные тесты реального
  HTTP-обработчика и Ledger через `httptest.NewRequest` / `NewRecorder`.
  Сценарии `ok`, `exceeded`, `cumulative_exceeded`, `bad_json` и другие
  оформлены отдельными подзадачами `t.Run`.

HTTP-тесты проверяют цепочку POST бюджета → POST транзакции → GET списка,
статусы 201/200/400/409, поля JSON и назначенный ID, единый `Content-Type`
и формат ошибок. Отдельно проверяются маппинг внутренних ошибок в 500,
логирование и конкурентные запросы с уникальными ID.

Каждый сценарий с состоянием вызывает `ledger.Reset()` до запуска и через
`t.Cleanup` после завершения. Такие сценарии выполняются последовательно;
горутины теста конкурентных запросов завершаются до очистки хранилища.
`Reset` предназначен для тестов, он не является HTTP-эндпоинтом.

### Запуск тестов и отчётов покрытия

Модули тестируются отдельно: `go test ./...` из корня репозитория не включает
вложенные модули. Из корня репозитория выполните:

```sh
cd ledger
go test ./... -cover -coverprofile=cover.out
go tool cover -func=cover.out
go tool cover -html=cover.out -o cover.html

cd ../gateway
go test ./... -cover -coverprofile=cover.out
go tool cover -func=cover.out
go tool cover -html=cover.out -o cover.html
```

Отчёты создаются в `ledger/cover.html` и `gateway/cover.html`.
`cover.out` и `cover.html` исключены из Git и формируются локально.

Для проверки гонок, повторяемости и независимости порядка запуска выполните
в каталоге каждого сервиса:

```sh
go test ./... -race -shuffle=on -count=3
go vet ./...
```

Достигнутое покрытие операторов по отчётам `go test -cover` и `go tool cover`:

| Область | Покрытие |
| --- | --- |
| Доменный пакет `ledger` | 100,0% |
| HTTP-пакет `gateway/internal/api` | 96,7% |
| Модуль Ledger целиком, включая `cmd/demo` | 56,5% |
| Модуль Gateway целиком, включая `main` | 90,8% |

Функции `main` запуска сервера и демонстрации не покрываются этими тестами.
В HTTP-пакете не покрыты повторная ошибка `SetBudget` после успешной валидации
и ошибка записи ответа. Проверки сосредоточены на валидации, бизнес-правилах,
целостности данных и HTTP-контракте.

## Тема 5. REST API в Gateway

HTTP-слой расположен в `gateway/internal/api`: DTO запросов и ответов,
преобразования в модели Ledger, маршруты, обработчики и middleware логирования.
Используется стандартный `net/http`, внешние библиотеки не требуются.

### Запуск сервера

Из корня репозитория (Go 1.22 или новее):

```sh
cd gateway
go run .
```

Сервер слушает `:8080`. Хранилище находится в памяти процесса Gateway и при
запуске пустое; после перезапуска данные теряются. Отдельно запускать Ledger
не нужно. Вызовы Ledger из HTTP синхронизированы для параллельных запросов.

### Эндпоинты

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/transactions` | Создание транзакции: 201 и объект с назначенным `id` |
| GET | `/api/transactions` | 200 и массив транзакций, изначально `[]` |
| POST | `/api/budgets` | Создание или обновление бюджета по категории: 201 и объект бюджета |
| GET | `/api/budgets` | 200 и массив бюджетов, изначально `[]` |
| GET | `/ping` | 200 и `{"message":"pong"}` |

Все ответы имеют `Content-Type: application/json; charset=utf-8`.
Ошибки возвращаются в формате `{"error":"описание"}`:

- 400 — неверный JSON, сумма/лимит не положительны или категория пустая;
- 409 — превышение бюджета: `{"error":"budget exceeded"}`;
- 500 — неожиданная внутренняя ошибка, её подробности выводятся только в лог;
- 404 — неизвестный путь; 405 — неподдерживаемый метод (с заголовком `Allow`).

Тело POST должно содержать один JSON-объект размером не более 1 МиБ.
Неизвестные поля отклоняются. Суммы и лимиты — целые числа в копейках.
`description` и `date` — необязательные строки; формат даты не проверяется,
как и в теме 4. Лимит учитывает сумму всех транзакций той же категории.
Для категории без бюджета расходы разрешены без ограничения.
Middleware логирует метод, путь и длительность каждого запроса, включая ошибки.

### Примеры cURL

Во втором терминале, после запуска сервера:

```sh
# До создания данных оба запроса возвращают [].
curl -i http://localhost:8080/api/transactions
curl -i http://localhost:8080/api/budgets

# Создать бюджет: 201. Повторный POST обновляет лимит этой категории.
curl -i -X POST http://localhost:8080/api/budgets \
  -H 'Content-Type: application/json' \
  -d '{"category":"еда","limit":500}'

# Создать транзакцию: 201, включая id, amount, category, description, date.
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":450,"category":"еда","description":"ланч","date":"2025-09-10"}'

# Суммарные расходы 550 превысят лимит 500: 409, budget exceeded.
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":100,"category":"еда"}'

# Невалидная сумма: 400. Объект не сохраняется.
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":0,"category":"еда"}'

curl -i http://localhost:8080/api/transactions
curl -i http://localhost:8080/api/budgets
```

### Самопроверка API

Из каталога `gateway`:

```sh
go test -race ./...
go vet ./...
```

Тесты проверяют пустые списки, DTO, создание и обновление, валидацию и неверный
JSON, ограничения бюджета, статусы 400/409/500, заголовки и формат ошибок,
маршрутизацию, логирование и уникальные ID при параллельном добавлении.

## Тема 4. ООП — интерфейсы и валидация в Ledger

Код задания находится в [`ledger`](ledger).

- `Validatable` объявляет единственный метод `Validate() error`.
- `Transaction.Validate()` проверяет положительную сумму и непустую категорию.
- `Budget.Validate()` проверяет положительный лимит и непустую категорию.
- Категории из одних пробелов также отклоняются. Суммы и лимиты заданы в копейках.
- `Date` хранится строкой; проверка формата пропущена, как разрешено в задании.
- Методы валидации только возвращают ошибки. Их вывод выполняется в `main`.
- `AddTransaction` и `SetBudget` вызывают `Validate()` до изменения хранилища.
  Загрузка бюджетов из JSON также проходит через `SetBudget` и возвращает ошибки.
- `CheckValid(v Validatable) error` демонстрирует полиморфизм: в `main`
  ей передаются корректные и некорректные транзакции и бюджеты через общий интерфейс.
- Сохраняется проверка суммарных расходов по категории: сумма до лимита включительно
  разрешена, превышение отклоняется; категории без бюджета не ограничены.

### Запуск

Требуется Go 1.22 или новее. Из корня репозитория:

```sh
cd ledger
go run ./cmd/demo
```

Запускать Ledger нужно из его каталога: там находится `budgets.json`.
Пример показывает результаты валидации двух типов, загрузку и обновление бюджетов,
отказ при превышении бюджета и нулевой сумме, затем список сохранённых транзакций.

### Самопроверка

```sh
cd ledger
go test ./...
go vet ./...
```

Тесты проверяют оба типа через `CheckValid`, отказ при неверных данных без
сохранения, защиту существующего бюджета от неверного обновления, загрузку JSON,
расходы ровно до лимита, превышение суммарного бюджета, категории без бюджета,
последовательные ID и возврат копии списка транзакций.

Остальные модули проверяются отдельно из корня репозитория:

```sh
go test ./...
cd gateway
go test ./...
```
