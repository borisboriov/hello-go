# Выбор технологий для трёх технических заданий

## ТЗ 1. High-Performance Blog Caching System

**Выбор: Memcached**

| Требование | Как закрывает Memcached |
|---|---|
| Кэш HTML, JSON, статей | Простое key-value хранилище: ключ → произвольная строка/байты до 1 МБ |
| Чтение < 1 мс | Данные только в RAM, операции O(1), многопоточный сервер — типичная задержка десятки–сотни микросекунд |
| Потеря данных допустима | Персистентности нет вообще — это и не нужно, кэш прогревается заново из PostgreSQL |
| Горизонтальное масштабирование | Узлы независимы, распределение ключей делает клиент (consistent hashing) — новый узел просто добавляется в список |
| Простота | Минимум команд (`get`/`set`/`delete`, TTL), вытеснение по LRU, почти нулевая настройка |

Схема работы — **cache-aside**: приложение ищет ключ в Memcached, при промахе
читает из PostgreSQL и кладёт результат в кэш с TTL. Для целых HTML-страниц
можно дополнительно поставить перед приложением Nginx/Varnish или CDN.

**Альтернатива: Redis.** Тоже подходит и так же быстр, но его возможности
(структуры данных, персистентность, репликация) здесь избыточны, а ТЗ прямо
требует максимальной простоты. Memcached к тому же многопоточный и лучше
использует все ядра одного узла для простых `get`/`set`.

## ТЗ 2. Real-Time Analytics and Recommendation Service

**Выбор: Redis (Redis Cluster) + Kafka как шина событий при миллионах событий/с**

| Требование | Как закрывает Redis |
|---|---|
| Счётчики просмотров | `INCR`/`INCRBY`/`HINCRBY` — атомарны, без блокировок и гонок |
| Списки последних действий | `LPUSH` + `LTRIM` — «последние N действий пользователя» |
| Рейтинги | Sorted Set: `ZINCRBY`, `ZREVRANGE` — топы статей/товаров за O(log N) |
| Очереди событий | Redis Streams (`XADD`, consumer groups) или списки (`BRPOP`) |
| Минимальная задержка | Всё в памяти, субмиллисекундные операции; сложная логика — атомарно через Lua / `MULTI` |
| Персистентность счётчиков | AOF (`appendfsync everysec`) + RDB-снимки; реплики для отказоустойчивости |
| Масштабирование | Redis Cluster шардирует ключи по 16384 слотам, узлы добавляются с решардингом |

Почему дополнительно **Kafka**: при миллионах событий в секунду удобно
принимать сырой поток кликов в Kafka (надёжный, реплицируемый журнал),
а обработчики (Go-сервисы или Flink) агрегируют события и обновляют
счётчики и рейтинги в Redis. Так Redis хранит «горячее» состояние
для быстрых ответов, а Kafka гарантирует, что события не потеряются.
Для долгих аналитических отчётов агрегаты можно сбрасывать в ClickHouse.

**Почему не Memcached:** нет атомарных операций над списками и
отсортированными множествами и нет персистентности — оба требования ТЗ
он не выполняет.

## ТЗ 3. User Profile and Configuration Management Service

**Выбор: Amazon DynamoDB** (managed NoSQL, serverless)

| Требование | Как закрывает DynamoDB |
|---|---|
| Структурированные и полуструктурированные данные | Документная/key-value модель: атрибуты, вложенные Map и List |
| Гибкость схемы | Обязателен только первичный ключ (`user_id`), у каждой записи свой набор полей |
| Доступность 99.99% | SLA 99.99% в одном регионе, 99.999% с Global Tables; данные реплицируются в 3 зоны доступности |
| Низкая задержка при любом объёме | Стабильные единицы миллисекунд на чтение/запись благодаря автоматическому шардированию по ключу; DAX — микросекунды для чтения |
| Минимальное администрирование | Нет серверов, патчей и ручного шардирования; on-demand-режим сам масштабирует ёмкость |
| Резервное копирование | Point-in-Time Recovery и on-demand бэкапы включаются настройкой |

Пример модели: таблица `Users` с ключом `PK = USER#<id>`; история подписки —
отдельные элементы с `SK = SUB#<дата>` в той же партиции; поиск по email —
через глобальный вторичный индекс (GSI).

**Альтернативы:** MongoDB Atlas (managed MongoDB — удобнее для сложных
запросов и агрегаций), Google Firestore или Azure Cosmos DB, если проект
живёт в другом облаке. Самостоятельно развёрнутые PostgreSQL/MongoDB
не подходят: противоречат требованию не управлять серверами, патчами и бэкапами.

## Итог

| ТЗ | Технология | Главный аргумент |
|---|---|---|
| 1. Кэш блога | Memcached | Максимально простой и быстрый in-memory кэш, персистентность не нужна |
| 2. Аналитика в реальном времени | Redis Cluster (+ Kafka) | Богатые атомарные структуры данных + персистентность |
| 3. Профили SaaS | Amazon DynamoDB | Serverless, 99.99% SLA, гибкая схема, нулевое администрирование |
